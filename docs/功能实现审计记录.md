## 3. 功能逐项核对

### 3.1 设备身份、发现与设备中心

调用链：`device-identity` → `discovery-service` / `core/discovery` → `main.js` IPC → `DeviceCenter.jsx`。

- 已实现稳定 `deviceId`、Ed25519 公钥指纹和 Device Schema。
- 已实现 UDP 49321 发现、重复设备合并、IP 更新、离线超时和身份变化标记。
- 本机设备由 `device:info` 单独加载并强制显示“在线·本机”，不显示配对/解除配对按钮。
- 远端设备根据发现资料、可信凭据和能力解析器显示状态。
- 能力展示使用 `supported/configured/available/verified/reasonCode`，避免只用平台名称判断。
- 风险：发现与能力声明属于远端自报，敏感操作仍必须经过配对授权；真实多网卡、跨网段和身份冲突场景仍建议继续回归。

### 3.2 安全配对与解除配对

调用链：`pairing-protocol` / `pairing-coordinator` / `pairing-relay` → `electron/security/pairing-service.js` → `main.js` IPC → `DeviceCenter.jsx`。

- 已实现一次性六位配对码、超时、错误尝试限制、允许/拒绝和状态查询。
- 配对成功后保存对端公钥、指纹及受保护授权；敏感接口按可信设备校验。
- 已实现身份指纹变化阻断、解除配对、本地撤销和离线时的本地立即失效。
- 配对码、私钥和令牌不进入发现广播或普通日志。
- 风险：本次自动化配对服务测试因本地监听 `EPERM` 未能复跑通过，双端人工验证已通过，需在正常开发机补跑。

### 3.3 SMB 共享与 macOS 挂载

调用链：Windows `ShareManager.jsx` → `main.js share:*` → `windows-share-acl.js`；macOS `MountManager.jsx` → `main.js mount:*` → `smb-mount.js`。

- Windows 共享创建、ACL 校验和必要时重建授权均保留平台边界。
- Windows 端使用用户提供的现有本地账号和密码，不再自动创建账号；密码输入框隐藏明文，并明确提示 Microsoft 联机账号可能无法用于 SMB。
- macOS 支持手动 `mount_smbfs` 与用户级自动挂载；主机密码统一维护，卸载会清理挂载点。
- 共享清单不传输 SMB 密码和远端绝对路径；Mac 端凭本机主机密码复用。
- 轻量 API 已接入挑战—签名—清单流程，界面可切换 SSH/轻量 API 以便迁移验证。
- 风险：SMB 的最终可用性仍受 Windows 本地账号、共享 ACL、NTFS 权限和系统网络策略共同影响，不能仅凭 API 清单判断挂载一定成功。

### 3.4 群聊与聊天记录管理

调用链：`ChatPage.jsx` → `preload.js` → `chat-server.js` / `chat-storage.js`。

- 已支持实名消息、SSE、心跳、幂等发送、回复引用、搜索和历史管理。
- 已支持拖拽文件、文件夹 ZIP、常见文本/图片/压缩格式；附件大小和数量由服务端校验。
- 发送区附件入口已精简，菜单可通过点击外部区域关闭；输入框支持右键粘贴。
- Windows 本机管理窗口可统计缓存、显示本机路径、导出和清理缓存/历史。
- 风险：聊天集成测试同样受本地端口监听限制；手机网页必须继续保持“聊天与下载 בלבד”的产品边界。

### 3.5 P2P 原生文件传输

调用链：`TransferPage.jsx` → `preload.js transfer:*` → `transfer-client.js` → 对端 `transfer-server.js` → `core/transfer.js`。

- 已实现传输提议、接收确认、一次性授权、分块传输、乱序块、状态查询、暂停/恢复/取消和 SHA-256 校验。
- 文件夹可先打包 ZIP；接收端使用临时文件，校验后原子移动，远端不能指定本机保存目录。
- 已接入 Ed25519 挑战签名和 transferId 绑定，未配对设备不能进入敏感传输流程。
- UI 已提供发送、接收、队列和进度状态。
- 风险：文档仍将双机大文件吞吐和断线恢复列为 P6/待真实验证；自动化传输服务测试本次因监听 `EPERM` 失败，不能仅凭代码视为完整验收。

### 3.6 文件夹同步

调用链：`SyncPage.jsx` → `sync-service.js` → `sync-server.js` → `core/sync-engine.js`。

- 已实现多任务、单向主从、配对码关联、任务启停、运行中锁定、监听+定时全量校验、失败补偿和回收区。
- 同步端口为 7892，服务设置和健康检查已纳入端口模型。
- 已使用配对公钥鉴权和分块传输，停止状态可联动通知对端。
- 风险：端到端同步测试本次全部受本地监听 `EPERM` 影响，需在可启动本地服务的环境重新验证。

### 3.7 WOL 与访问记录

调用链：`DeviceCenter.jsx` → `main.js wol:* / access:*` → `wol-service.js` / `core/wol.js` / `core/access-log.js`。

- WOL 仅对已配置目标 MAC 和广播地址的设备显示可操作状态；发送魔术包后轮询上线并记录验证结果。
- 访问记录只记录实际访问过本机服务的设备，不主动扫描或向陌生设备发包。
- 风险：真实关机唤醒仍依赖 BIOS、网卡、电源和有线网络，必须在目标硬件上单独验证。

### 3.8 服务设置与端口健康检查

调用链：`ServiceSettings.jsx` → `preload.js services:*` → `main.js` → `core/service-health.js`。

- 已集中展示健康检查、端口信息、占用状态、占用来源/预期服务和可用候选端口。
- 修改端口后返回 `restartRequired`，界面提示重启应用生效。
- 固定默认端口：聊天 7890、配对 7891、同步 7892、传输 49152 起始并支持回退。
- 风险：端口扫描只能说明监听状态，不能替代防火墙、路由和双端协议连通性验证。

## 4. 本次检查的失败解释

本次 `npm run check` 的 lint 已通过。123 项测试中 36 项失败，错误集中为 Node 测试尝试监听 `127.0.0.1` 或 `0.0.0.0` 时收到 `EPERM`，涉及群聊、配对服务、共享清单、同步和传输服务集成测试。该结果说明当前执行环境限制了本地 socket 监听，不能直接解释为业务逻辑失败；应在关闭开发实例、允许本地端口监听的开发机上复跑并记录新的真实结果。

## 5. 当前风险与建议顺序

1. 先清理并审阅未提交改动，确认 `.workbuddy/` 等临时内容不进入发布版本。
2. 在可监听本地端口的环境重新执行 `npm run check`，逐项处理真正的业务失败。
3. 复核 README 中“123 项全绿”与当前真实结果是否一致，只有复跑通过后才能保留该表述。
4. 完成一次双机大文件传输、同步断线恢复和 WOL 实机验证，分别记录设备、文件大小、耗时和结果。
5. 审计通过后再提交代码、创建版本标签和生成安装包；在此之前不把当前工作区直接称为最终发布包。

## 6. 下一轮逐功能复核模板

每个功能改动都按以下顺序复核：

`界面入口 → preload IPC → main 编排 → core/平台适配 → 服务端鉴权 → 错误码/中文提示 → 自动化测试 → 双机验证 → 文档更新`

记录时必须同时写明：已验证事实、未验证边界、失败是否由环境造成，以及是否影响数据安全或用户数据。
