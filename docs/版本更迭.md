## 常见问题、坑与解决方案

### 1. Node、Electron 和依赖安装

| 现象 | 原因 | 处理方式 |
| --- | --- | --- |
| `npm install` 卡在 Electron 下载 | GitHub 直连不稳定 | 使用启动脚本，或当前 shell 设置 `ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/` 后执行 `npm run electron:ensure` |
| `npm install` 显示 `up to date` 但 Electron 二进制不存在 | Electron 44 起 npm 包不再依赖 `postinstall` 自动下载二进制 | 执行 `npm run electron:ensure`；它会用镜像调用 `node node_modules/electron/install.js` 并复验平台可执行文件 |
| Node 版本不对 | 项目依赖 Electron 44 和 Node 24 API/安装链路 | 使用 Node `v24.19.0`；执行 `npm run runtime:check` 验证 |
| Electron 二进制不完整或提示 `Electron failed to install correctly` | npm 脚本被拦截或下载中断 | 先确认 Node 版本，再确认 `node_modules/electron`；必要时执行 `npm approve-scripts electron` 后重新 `npm install` |
| 运行时找不到 Electron | 只复制了源码，未安装依赖 | 不要复制 `node_modules`，在目标机器执行 `npm install` |

项目不应混用旧 Node 22/Electron 33 的锁文件；升级运行时后必须使用当前 `package-lock.json`。

### 端口和 Windows 脚本注意事项

- Vite 默认端口不使用 5173；Windows 本机的 Hyper-V/WSL2 可能保留 `5115-5214`，统一版使用 `6300`。
- `package.json` 的 `dev`、`vite.config.mjs` 和 `wait-on` 必须保持 6300 一致，否则会出现 Vite 已启动但 Electron 连接不到页面。
- `启动 InnerNet.bat` 必须保持 CRLF 换行。若从 macOS 同步后变成 LF，cmd 可能把 `errorlevel` 拆坏，出现“po/errorlevel 不是命令”或弹出 `C:\WINDOWS\system32\nul`。编辑后请用 Windows 编辑器或 Git 的 CRLF 设置恢复。

### 2. Windows 共享创建、ACL 和管理员权限

共享创建、读取共享级 ACL 都需要管理员权限。Windows 端请使用“以管理员身份运行”的 PowerShell，或让应用执行内置提权。

正确的共享级 ACL 应类似：

```powershell
Get-SmbShareAccess -Name "共享名" | Format-List AccountName,AccessRight,AccessControlType
# AccountName: BRZ\brz
# AccessRight: Full
# AccessControlType: Allow
```

注意事项：

- 裸用户名 `brz` 在部分 Windows SMB 授权调用中可能被错误解析成 `BRZ\`（空用户名），最终导致 macOS `Permission denied`。
- `Grant-SmbShareAccess` 失败时，程序会保留原路径和描述，删除共享对象，用规范化的 `机器名\用户名` 重建，再次验证 ACL；共享目录中的文件不会被删除。
- 不要使用 `icacls /inheritance:r` 作为共享创建前的“加固”。它会切断目录继承，造成资源管理器重新授权甚至让 Node 把目录误判为不存在。当前实现使用 `/inheritance:e` 恢复继承，并仅补充必要的 `(OI)(CI)F` 权限。
- `fs.existsSync()` 返回 `false` 不一定代表路径不存在，也可能是 ACL 拒绝；排查时同时用资源管理器和 `fs.accessSync` 验证。
- 若 ACL 正常但枚举仍被拒绝，检查 360 等安全软件的文件保险箱、隐私保护或驱动拦截。

### 3. macOS 手动挂载

- `mount_smbfs -N` 读取的是 `~/Library/Preferences/nsmb.conf`，不是钥匙串；错误依赖它会造成反复询问密码。
- 当前实现将主机、账号、密码、共享名分别按 RFC 3986 编码，并通过参数数组调用系统命令，避免中文/空格解析错误和 shell 泄漏。
- 挂载前先检查 Windows TCP 445；若 `No route to host` 或端口不可达，应先处理网络、防火墙和 Windows 共享状态，不要重复输入密码。
- 重复点击已挂载共享是幂等操作，会提示无需重复挂载，不再误报 ACL 或错误 64。
- 卸载成功后只删除空挂载目录；目录非空时保留，避免误删用户文件。

### 4. macOS 自动挂载

旧方案直接写 `/etc/auto_master`，在新 macOS 上会遇到 `/bin/printf: No such file or directory` 或 `Operation not permitted`。原因是系统路径/SIP 限制，不是用户密码问题。

当前自动模式改为当前用户的 LaunchAgent：登录启动、每 30 秒检查、网络恢复后自动重挂，不修改 `/etc/auto_master`，不需要关闭 SIP。开发验证直接重启 `npm run dev`，无需每次打包 DMG。

### 5. 轻量 API 同步清单（取代 SSH 免密通道）

- 原方案要求 Windows 安装并配置 OpenSSH Server（改端口、放行防火墙）、Mac 生成密钥并粘贴到 Windows 的
  `authorized_keys` 完成授权，任何一步没对上就拉不到清单。2.0 已整体移除这条链路。
- 现方案复用配对时交换的 Ed25519 公钥：Mac 先向 Windows `7890` 端口取一次性挑战，用本机私钥签名后
  换取清单，Windows 用配对时留存的公钥验签。挑战含 `deviceId` / `requesterId` / `nonce` 和过期时间，
  只签发给已配对设备，避免重放和跨设备冒用。
- 清单只含 `shareName` / `account` / `unified`，**SMB 密码不再随清单传输**。原 SSH 清单里带明文口令，
  换成 HTTP 后等于在局域网上裸奔，因此改为由 Mac 在本机保存复用。
- 路由由主进程注入签发器/校验器后才注册；未注入时请求返回 404 而不是放行，避免“接口在但没鉴权”的空窗。
- Windows stderr 按 GBK 解码并提供 UTF-8 回退，中文错误不再显示乱码。

### 6. 共享名、路径和命令参数

- 共享名包含中文或空格时，Windows 创建和 macOS 挂载都必须分别编码；不要自行拼接 shell 字符串或手动添加多层引号。
- `net share` 的 `共享名=路径` 必须作为一个参数 token 传入；统一版使用 Node 参数数组处理空格。
- 临时脚本放在无中文、无空格的临时目录，减少 PowerShell 5.1 编码和路径解析问题。
- 建议源码目录使用不含空格的路径；共享真实目录可以包含中文和空格。

### 7. 群聊和缓存

- Windows 端启动群聊服务，Mac 端填写 Windows IP 和端口；手机浏览器打开 `http://<WindowsIP>:7890/`。
- 群聊附件由服务端按白名单和大小再次验证，不能只依赖浏览器端校验。
- 清理聊天记录优先使用 Windows“记录管理”窗口：清空记录会保留附件，随后可用“清理无引用缓存”回收；“全部清空”才会删除全部附件。
- 不要通过局域网 HTTP 自行删除 `messages.jsonl` 或缓存目录；远程客户端没有删除权限，避免误删共享主机数据。

### 8. 群聊 P1-P2

- P1：桌面端增加未读计数和系统通知开关；窗口不在前台时收到他人消息会计入未读，首次启用通知时请求系统授权。
- P1：聊天记录管理窗口支持 JSON/Markdown 导出，并可按消息 ID 删除指定记录；删除通过 Windows 本地 IPC 执行并广播 reset，远程客户端不会获得文件系统删除权限。
- P2：消息中的 `@昵称` 自动高亮。

## 2026-08-27：P4 原生传输安全基础

### 问题

- 原传输服务只完成了分块写入基础，尚未形成“提议→接收确认→授权→发送”的闭环。
- 端点曾允许以普通令牌进入分块流程，授权没有严格绑定具体 `transferId`。
- 乱序传输时，首个到达的非 0 分块可能因为临时文件尚未创建而失败。
- 测试使用固定 `49152` 端口，失败后可能遗留 Node 监听进程，导致后续测试误报端口占用。

### 解决思路

1. 传输授权必须绑定双方设备、具体 `transferId`、配对授权和有效期。
2. 传输提议和状态查询必须先通过配对授权；接收决定只允许在接收端本机 IPC 执行，远端不能指定保存目录。
3. 接收端先预分配临时文件，再按块偏移写入，允许乱序到达。
4. 测试服务使用随机端口；固定端口只保留给实际运行服务。

### 解决方法

- `core/transfer.js` 增加 `createTransferAuthorization`、`encodeTransferToken`、`decodeTransferToken`，并在 `authorizeTransfer` 中校验 `transferId`、接收设备和有效期。
- `electron/transfer-server.js` 增加受授权的提议/状态边界、分块长度校验、`accepted` 状态校验、安全 ID 校验和临时文件预分配。
- `electron/transfer-client.js` 增加原生流式分块发送，按文件块读取并报告进度，不把大文件整体载入内存。
- 接收端决定接口拒绝 HTTP 直接设置 `token` 或 `targetDir`，目录选择保留在本机 IPC 边界。
- 传输服务测试改用随机端口，新增乱序分块、危险 ID、授权绑定和流式发送测试。

当前 P4 仍未宣称完整通过：双端传输提议 UI、接收目录选择界面、队列、暂停/恢复真实双机流程和大文件跨设备验证待完成。

> **2026-08-30 更新**：P4 已在批量重构中接通完整链路（`TransferPage.jsx` 三块布局 + offer/sends/listOffers/decide/status IPC + 文件夹 zip 打包 + 挑战按配对公钥签发与校验 + token 鉴权），见本文末「批量功能修正与重构（8 项）」。双机真机端到端大文件验证与真实吞吐测试仍属 P6。


## 2026-08-27：P4 传输端口占用修复

### 问题

传输服务默认使用 TCP `49152`。当旧实例、残留测试进程或其他程序已占用该端口时，应用日志会出现 `EADDRINUSE`，双端发现到的传输端口也可能失效。

### 解决方法

- `electron/transfer-server.js` 现在从 `49152` 开始自动尝试后续 10 个端口，端口被占用时不再直接启动失败。
- 服务返回实际监听端口，设备发现公告同步实际 `transfer` 端口，发送端按公告连接。
- 传输测试统一使用随机端口，避免测试之间互相污染。
- 传输端点仍要求授权和 accepted 会话，端口回退不会放宽安全边界。

如果仍看到连续 10 个端口都被占用，应检查是否重复启动了多个应用实例或有其他程序占用 `49152-49202`。

## 2026-08-28：统一安全闭环梳理

### 唯一安全链路

1. **设备身份**：首次启动生成稳定 Ed25519 身份和 SHA-256 指纹；私钥只保存在本机受保护目录，不进入发现广播。
2. **设备发现**：UDP 仅广播最小公开信息（设备 ID、名称、指纹摘要、服务端口）；发现结果默认是 `unpaired`，不能直接执行敏感操作。
3. **人工配对**：发起端提交目标设备 ID，接收端本机显示一次性 6 位验证码；双方核对后由接收端确认。验证码 5 分钟有效，最多 5 次尝试。
4. **信任建立**：确认成功后双方保存对端指纹和短期配对授权；身份指纹变化进入 `identity_changed`，必须解除旧信任后重新配对。
5. **能力门控**：文件传输、挂载、WOL 等敏感能力必须同时满足“平台支持、服务在线、设备已信任”；群聊发现不等于传输授权。
6. **传输授权**：每次传输创建唯一 `transferId` 和版本化 manifest，授权绑定发送/接收设备、配对授权、transferId 和过期时间；提议、状态、分块接口均校验授权。
7. **接收确认**：接收决定只能在接收端本机 Electron IPC 执行，远端不能指定保存目录；确认后才进入 `accepted`，完成分块后校验 SHA-256 并原子落盘。
8. **撤销与失效**：取消、拒绝、过期、身份变化或解除配对都会使后续操作失败；临时文件不得直接作为最终文件。

### 明确废止的旁路

- 不使用未配对设备直接传文件。
- 不把私钥、明文密码或长期授权令牌放入发现广播、React 网络请求或普通日志。
- 不接受 HTTP 远程设置接收目录或直接批准传输。
- 不以“端口可连接”代替“设备已信任”。
- 不将 SMB 管理权限与 P2P 传输授权混用；两者分别受平台权限和配对信任控制。
- 不通过共享清单接口下发 SMB 口令；口令只存本机，任何情况下都不随清单出网。

当前代码已具备身份、发现、配对、凭据存储、传输 manifest/状态机和端点授权基础；P4 完整 UI/IPC 接线仍需按上述单一路径完成，不再新增第二套授权机制。


## 2026-08-28：P4 服务端挑战签名接入

- **问题**：如果由发送端自行生成挑战，或通过普通 HTTP 状态接口传递配对码/授权，局域网监听者可能构造签名请求或截获敏感凭据。
- **思路**：挑战必须由接收端服务端生成，并绑定已确认的配对会话、双方设备 ID、`transferId`、随机 nonce 和有效期。
- **实现**：配对服务新增受会话保护的传输挑战接口；接收端使用本机 Ed25519 私钥签名；主进程新增 `transfer:requestChallenge` IPC，供传输提议前置调用。客户端不能自带 nonce 或替换目标设备。
- **安全边界**：未确认配对会话、设备不匹配、参数无效或挑战过期时拒绝；私钥不离开主进程。
- **后续**：将签名挑战验证接入 `/api/transfer/offer`，再接收端本机确认和分块授权。


### 签名挑战接入对网内用户的影响

- 仅影响 P2P 文件传输提议和授权，不影响 SMB 挂载、Windows 共享、群聊、设备发现和服务端口检查。
- 已完成配对的设备信任记录不会被清除，但双方需要升级到支持签名挑战的版本才能传输文件。
- 未配对设备仍可看到最小化发现信息，但不能发起受信任传输。
- 旧版本客户端发起的未携带签名挑战的传输提议会被拒绝；旧版本的其他功能继续可用。
- 接收端保存目录、确认、取消等动作继续留在本机 Electron IPC，网内其他用户无法远程指定目录或代替确认。

## 2026-08-30：解除配对双向同步（撤销凭据）

### 问题

- `pairing:unpair` 只删本机凭据，对端完全不知情：A 解除后显示「待配对」，B 仍显示「已信任」。
- B 之后的共享清单拉取、P2P 传输全部被拒，却拿不到任何解释，只能看到笼统的「认证失败」。
- 信任状态是纯本地计算的（发现广播不含 trust 字段），对端没有任何途径感知变化。

### 解决方法

- 新增 `core/revocation.js`：撤销凭据带 `deviceId` / `targetDeviceId` / `issuedAt` / `expiresAt`，
  由解除方用本机 Ed25519 私钥签名。不需要先取一次挑战 —— TTL 兜住重放，删除操作本身幂等。
- 配对服务新增 `POST /api/pair/revoke`：只认本机信任过的设备，并用配对时留存的公钥验签。
  不签名的话，局域网内任何人都能伪造撤销把两端的配对拆掉。
- `pairing:unpair` 改为「先删本机凭据，再通知对端」，返回 `delivered`；对端离线时本机同样立即生效，
  界面明确提示「未能送达通知，对方下次尝试操作时会自动解除」。
- 兜底被动降级：共享清单拉取返回 403、传输挑战被拒时，本机自动解除对该设备的信任并在日志里说明原因，
  覆盖「撤销通知没送达」的残留场景。
- 界面区分「从未配对」与「已被对方解除信任」：被解除方直接收到「XX 已解除与本机信任」提示，
  而不是毫无解释地变回「待配对」。

### 顺带修掉的隐患

- 发起方（Mac）此前只在对端记录里存了 fingerprint、没存 publicKey，导致 Windows 主动解除时
  Mac 验不了签。`/api/pair/status` 现在回传 `identityPublicKey`，双方都留存对端公钥。
- 与轻量 API 同步同理：升级后旧的配对记录里缺少 publicKey，**需要解除配对后重新配对**。

## 2026-08-30：Mac 端按主机维护 SMB 统一密码

### 背景

Windows 必须创建本地 SMB 账号并设置密码（Mac 才能挂载）；但 Mac 端每条共享
独立存 password，N 个共享要填 N 次，新同步的共享又是空的。
同时 Windows 端把密码明文晒在卡片上，不雅观。

### 解决

- 新增 `hostCredentials.json`（与配对凭据同套加密），按 host 维护 SMB 统一密码。
- 主机账号维护区：列出所有出现过的主机，可「设置/更新/删除」；设置/更新时
  按用户选择自动覆盖该主机所有现有共享的 password。
- 共享级 `password` 字段保留作为特例/覆盖用；缺省时 `mount:mountOne` 与
  `mount:applyAutofs` 自动回退到主机密码（解析时不动原始记录，autofs
  脚本里把口令写进去再生成 LaunchAgent）。
- 同步时新共享 password 为空也能挂载（用主机密码）。
- Windows 端密码默认 •••••••• 遮罩，旁加眼睛按钮可单独临时显示，「复制连接信息」仍复制真实密码。

## 2026-08-30：文件夹双端同步（单向主从、实时模式、回收区）

### 功能

指定文件夹的双端实时同步。在顶部新增「文件夹同步」标签页配置。

### 设计取舍

- **单向主从**：主端是唯一事实来源，变更推送到从端；主端删除的文件在从端
  移入 `.innernet-trash/` 回收区（可恢复，超期自动清理）；从端多余的文件
  在全量校验轮也清进回收区。不做双向合并，主端永远赢。
- **触发方式**：`fs.watch` 递归监听 + 800ms 防抖保证实时性；另加 5 分钟
  全量校验抗事件丢失（size+mtime 比对，rsync 同款；同秒同字节变更靠
  全量轮兜底，不逐文件算 sha256）。
- **鉴权**：复用配对时交换的 Ed25519 公钥验签，与共享清单接口同一套机制。
  未配对设备拿不到挑战，无法推送或拉取文件清单。
- **回收区**：主端删除 → 从端文件移入 `.innernet-trash/<时间戳>/<原路径>/`，
  默认保留 7 天，可在界面手动恢复或清空。

### 实现分层

| 模块 | 职责 |
|---|---|
| `core/sync-engine.js` | 纯函数：扫描、差异计算、回收区路径、过期清理、退避 |
| `electron/sync-server.js` | 从端 HTTP 端点：challenge/list/begin/chunk/commit/trash/purge |
| `electron/sync-service.js` | 主端编排：监听、轮询、同步周期、重试、索引持久化、回收区维护 |
| `src/components/SyncPage.jsx` | UI：角色、目录、对端、启停、状态、历史、回收区 |
| 端口 `7892` | 同步服务，加入服务健康检查 |

### 注意

- macOS 从端不要把目录落在 SMB 挂载卷上 —— `fs.watch` 在网络卷上不可靠。
- 同步是单向的，从端的本地改动会在下一轮被主端覆盖或清进回收区。
- 大文件按 4MB 分块传输，每块独立校验，断点续传靠 missing 列表。
